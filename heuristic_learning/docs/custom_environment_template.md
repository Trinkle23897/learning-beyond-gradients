# Custom Environment Template

Use this checklist for RL environments that need their own adapter, opponent
protocol, replay handling, tournament logic, or report generator instead of the
shared Gymnasium evaluator.

## Required Code Layout

Create the initial artifact tree, planned registration/policy files, skipped test scaffolds, and custom command placeholders with `make scaffold-custom-env ENV=<EnvId>`. This target sets `REGISTRATION.custom_module` to `hl_benchmark.custom_envs.<env_slug>`. Then replace the generated TODO command modules with real environment logic before registering the env as `custom_active`.

```text
hl_benchmark/environments/<env_slug>.py      # auto-discovered REGISTRATION metadata
hl_benchmark/policies/<env_slug>.py          # transparent policies, archives, SUPPORTED_POLICY_NAMES, make_policy(), candidate_configs()
hl_benchmark/custom_envs/<env_slug>/__init__.py
hl_benchmark/custom_envs/<env_slug>/adapter.py           # dependency/API compatibility layer
hl_benchmark/custom_envs/<env_slug>/evaluate.py          # fixed-seed evaluation command
hl_benchmark/custom_envs/<env_slug>/search.py            # scalar/config search, dev seeds only
hl_benchmark/custom_envs/<env_slug>/summarize.py         # ledger-to-summary regeneration
hl_benchmark/custom_envs/<env_slug>/report.py            # final report generator
hl_benchmark/custom_envs/<env_slug>/performance_report.py # score-focused explanation generator
hl_benchmark/custom_envs/<env_slug>/audit.py             # artifact and anti-cheating checks
```

Optional custom modules include `opponents.py`, `tournament.py`, `doctor.py`,
`final_eval.py`, and replay/diagnostic helpers.

## Required Artifact Layout

Create the standard artifact tree and code placeholders with `make scaffold-custom-env ENV=<EnvId>` for custom harnesses. Use `make scaffold-generic-env ENV=<EnvId>` for normal Gymnasium envs, or `make scaffold-env ENV=<EnvId>` when only artifacts are needed. Do this before promoting the environment to runnable status.

```text
experiments/<env_slug>/
  README.md
  configs/.gitkeep
  results/.gitkeep
  reports/.gitkeep
  notes/.gitkeep
```

Generated after evaluation/report commands:

```text
experiments/<env_slug>/
  results/trials.jsonl
  results/summary.csv
  results/audit_latest.json  # generated by custom-verify or audit --output
  reports/final_report.md
  reports/requirements_audit.md  # optional coverage matrix for mature custom environments
```

The README must identify the exact environment ID and artifact root, and each required subdirectory keeps a `.gitkeep` placeholder until generated artifacts exist. The latest audit JSON is generated output, not scaffold state, so a planned custom env can omit `results/audit_latest.json` until its real audit command exists.

Keep `trials.jsonl` append-only. If a run is invalid, append a new row that
explains the invalidation instead of deleting or rewriting old evidence.

## Registration Status

- `planned`: metadata exists, but the environment is not runnable yet; scaffold TODO metadata is allowed until promotion.
- `custom_active`: runnable through the module root named by
  `REGISTRATION.custom_module`, normally `hl_benchmark.custom_envs.<env_slug>`,
  and excluded from generic `make eval-all`.
- `active`: included in the generic aggregate evaluator.

Use `custom_active` for adversarial, legacy, multi-agent, or replay-heavy
environments until they can honestly share the generic evaluator. The registry
auto-discovers modules with `REGISTRATION`; set `custom_module` to the
custom harness import root, set `suite_order` when stable benchmark ordering
matters, and keep environment IDs, keys, and artifact slugs unique. The policy module must expose runnable `initial`, `improved`, and `tuned`
entries in `SUPPORTED_POLICY_NAMES`, callable `make_policy()`, and
`candidate_configs()` so the central factory and generic search command can
dispatch without per-environment edits. `make check-env` verifies the required custom
adapter/evaluate/search/summarize/report/audit modules import successfully,
verifies callable custom command entrypoints, and fails if scaffold metadata
or scaffold/TODO markers remain in EnvSpec metadata, runnable sources, or the unreplaced generated skipped test scaffold. For
planned custom registrations, those import and entrypoint checks run as
scaffold-readiness checks while EnvSpec metadata remains a promotion-time gate.

## Minimum Test Coverage

- Registry metadata plus `planned_env_ids()` while scaffolded and `custom_env_ids()` after promotion.
- Action-space validity and policy output shape/type.
- Deterministic smoke evaluation on fixed seeds.
- Ledger schema validation and summary generation.
- Golden behavior checks on selected observations or short traces.
- Holdout guard: search and iteration commands must reject holdout/audit splits.
- Report-generation validation.

## Minimum Commands

During the planned phase, document and run scaffold/readiness commands only:

```bash
make scaffold-generic-env ENV=<EnvId>
make scaffold-env-code ENV=<EnvId>
make scaffold-env-tests ENV=<EnvId>
make scaffold-custom-env ENV=<EnvId>
make check-env ENV=<EnvId>
make check-env ENV=<EnvId> ARGS="--format json"  # inspect artifact_issues, test_scaffold_issues, planned_test_scaffold_issues, runnable_test_scaffold_issues, promotion_ready, promotion_blockers, runnable, metadata_issues, import gates, and custom command entrypoints
make check-promotion ENV=<EnvId>  # fails until promotion_ready is true
make check-promotions  # aggregate promotion readiness across registered envs
make check-envs  # reports runnable checks plus planned registry-entry visibility
make check-planned-envs  # strict planned scaffold gate: artifact, skipped-test identity, policy, custom-harness scaffold gate for CI
make verify  # non-evaluation registry/artifact/test gate
```

Do not treat custom command dispatch as a passing gate while the environment is
still `planned`; `make custom-run` and `make custom-verify` require a
`custom_active` registration with implemented command modules.

Before promoting to `custom_active`, document and validate the module command
contracts that the shared dispatcher will call:

```bash
python -m hl_benchmark.custom_envs.<env_slug>.evaluate --policy initial --split smoke
python -m hl_benchmark.custom_envs.<env_slug>.search --split dev
python -m hl_benchmark.custom_envs.<env_slug>.summarize
python -m hl_benchmark.custom_envs.<env_slug>.report
python -m hl_benchmark.custom_envs.<env_slug>.audit
python -m hl_benchmark.custom_envs.<env_slug>.audit --output experiments/<env_slug>/results/audit_latest.json
make custom-run ENV=<EnvId>
make custom-run ENV=<EnvId> CUSTOM_COMMAND=summary
make custom-run ENV=<EnvId> CUSTOM_COMMAND=report
make custom-run ENV=<EnvId> CUSTOM_COMMAND=audit
make custom-verify ENV=<EnvId>
```

The standard `custom-verify` command runs readiness checks, artifact-layout
validation, `summarize`, harness-declared `CUSTOM_VERIFY_EXTRA_COMMANDS`,
`report`, `performance_report`, optional `generation_report`, and
`audit --output <path>`. Use `CUSTOM_VERIFY_EXTRA_COMMANDS` for non-evaluation
diagnostics, protocol regeneration, or replay summaries that must be refreshed
before report/audit checks.
Custom verify extras reject evaluation, search, tournament, and final-holdout commands; keep those as explicit experiment runs.
Keep those command-line contracts stable before promoting the environment to
`custom_active`.
Do not add `custom-verify` to the default `make verify` target; custom verification
regenerates generated artifacts and should remain an explicit per-environment step.

For competitive environments, also document opponent-pool and tournament
commands. For final evidence, provide a one-shot holdout command that refuses to
run again unless explicitly overridden for audit.
